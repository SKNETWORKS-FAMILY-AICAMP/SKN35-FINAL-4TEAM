왜 이걸 쓰는가.

SlotAgent는 에이전트의 도구 구성을 같은 조건에서 시험하고, 성공률·비용·시간을 비교해 교체할 근거를 주는 서비스입니다. 그 일을 만드는 기술을 화면부터 판정까지 순서대로 정리했습니다.

핵심 원칙: 실험은 자체 엔진이 돌리고, 결과는 규칙과 통계로 판정합니다. AI는 도구 후보를 찾거나 결과를 설명할 수 있지만, 고도화 AI가 판정을 바꾸지는 못합니다.

02

기술별 역할과 선택 이유

역할이 가까운 기술을 묶었습니다. 아래 설명은 채택한 설계이며 모든 기능이 이미 구현됐다는 뜻은 아닙니다.

A. 화면 — 실험을 쉽게 설정하고 결과를 읽게 하기
화면 · 공동 / ① 1차

Next.js + TypeScript

서비스 화면을 만들고, 화면 코드의 데이터 실수를 줄입니다.

왜 쓰나요?

등록 → 후보 선택 → 실험 → 결과처럼 여러 화면을 한 구조에서 만들기 위해서입니다. TypeScript는 후보 ID나 결과 값의 형태가 잘못 연결되는 실수를 개발 중에 찾는 데 도움을 줍니다.

사용 예: “GitHub 조회 자리”의 후보 A·B를 고르고, 끝난 실험의 성공률과 비용을 나란히 보여 줍니다.
화면 구성 · ① 1차

Tailwind CSS + shadcn/ui
TanStack Query

화면 모양을 맞추고 서버의 최신 상태를 가져옵니다.

왜 쓰나요?
  • Tailwind CSS: 간격·색·화면 크기별 배치를 일관되게 만듭니다.
  • shadcn/ui: 버튼·표·입력창·승인창의 공통 모양을 맞춥니다.
  • TanStack Query: 실험 상태 조회·갱신을 화면마다 따로 만들지 않도록 합니다.
진행 화면은 일정 간격으로 상태를 다시 조회하는 폴링부터 시작합니다. 별도 실시간 통신은 필요해질 때 검토합니다.
B. 서버와 데이터 약속 — 네 사람이 만든 코드를 연결하기
API · 공동 / ① 1차

Python 3.12 + FastAPI

화면의 요청을 받아 실행·조회 기능으로 연결하는 서버입니다.

왜 쓰나요?

실행 엔진·채점·통계·모델 학습이 Python 중심이므로 API도 같은 언어로 연결합니다. FastAPI에는 등록·실험 생성·실행 요청·결과 조회 같은 입구를 맡깁니다.

“실행” 요청을 받으면 작업을 큐에 넣고 상태를 돌려줍니다. HTTP 요청 안에서 실험 전체가 끝날 때까지 기다리게 만들지 않습니다.
데이터 계약 · 4명

JSON Schema + jsonschema
json-schema-to-typescript

서버·화면·역할 사이에서 같은 데이터 약속을 씁니다.

왜 쓰나요?

각자 만든 코드가 마지막에 그대로 이어지려면 데이터 모양이 같아야 합니다. 원본은 contracts/ 하나로 두고, 서버는 jsonschema로 검사하며 화면 타입은 스키마에서 생성합니다.

스키마 → 서버 검사 + 화면 타입 생성
생성 위치: frontend/src/types/contracts.ts
같은 형식의 Pydantic 모델·TypeScript 타입을 손으로 중복 작성하지 않습니다.
C. 저장과 실행 — 중단돼도 근거가 남는 실험 만들기
DB · 4명 / 기반 ①

PostgreSQL 17 + psycopg 3

설정·문항·기록·비용·채점·판정을 저장합니다.

왜 쓰나요?

실험 후보와 문항, 실행 기록과 채점 결과처럼 서로 연결되는 데이터가 많습니다. 관계와 제약을 DB에서 확인하고 여러 결과를 한 번에 저장하는 트랜잭션으로 “일부만 저장된 완료 상태”를 막기 위해 사용합니다.

psycopg는 Python에서 PostgreSQL에 연결하는 도구입니다. ORM 없이 SQL을 사용하고, 접속 설정은 DATABASE_URL 하나로 맞춥니다.

작업 처리 · ①

DB 큐 sa_jobs + Python 워커

실행할 일을 DB에 쌓고 워커가 가져가 처리합니다.

왜 쓰나요?

실험은 오래 걸리고 중간에 워커가 끊길 수 있습니다. 어떤 작업을 누가 맡았는지와 다시 맡아야 하는지를 DB에 남겨 관리합니다. 작업 큐를 별도 시스템으로 나누지 않아 결과 상태와 함께 확인할 수 있습니다.

워커가 작업을 일정 시간 맡는 것을 임대라고 합니다. 오래된 워커가 뒤늦게 결과를 보내도 임대·시도 번호로 구분합니다. Celery·Redis 큐는 쓰지 않습니다.
실행 엔진 · ①

자체 실행 루프 + write_proxy

모델 응답 → 도구 실행 → 결과 전달을 직접 제어합니다.

왜 쓰나요?

우리 평가에는 도구 호출 순서·출력·비용·쓰기 시도까지 필요합니다. 자체 루프를 쓰면 제한 시간·취소·기록·재생을 우리 계약에 맞춰 제어할 수 있습니다. Inspect AI는 사용하지 않습니다.

단계마다 기록을 남기고, fake 방식의 쓰기 호출은 write_proxy가 가로채 “보내려던 내용”만 보존합니다. 다음 채점·분석 작업을 넣는 일은 advance.py가 담당합니다.
실행 격리 · ①

Docker

풀이마다 도구 실행 환경을 분리합니다.

왜 쓰나요?

이전 풀이의 파일이나 프로세스가 다음 풀이에 영향을 주면 공정한 비교가 어렵습니다. 도구 환경을 컨테이너로 나눠 풀이 간 영향을 줄이고 같은 환경을 다시 만들기 위해 사용합니다.

컨테이너 안에는 도구·연습 환경, 밖에는 루프·모델 호출·write_proxy를 둡니다. 모델 API 키는 컨테이너에 넣지 않습니다.
D. 채점과 통계 — “좋아 보인다”를 근거 있는 결과로 바꾸기
규칙 채점 ① · LLM 판정기 ②

규칙 채점 + 제한된 LLM 판정기

문항의 정답 조건을 충족했는지 확인합니다.

왜 쓰나요?

수치·집합·순서·금지 행동처럼 코드로 검사할 수 있는 것은 규칙으로 확인해 같은 기록에 같은 결과가 나오게 합니다. 규칙으로 보기 어려운 항목만 검증한 ② LLM 판정기에 맡깁니다.

“배포 이후 에러 수를 조회한 다음 공유했는가?”를 기록과 조건으로 확인합니다. 추천 에이전트가 자기 판단으로 채점 결과를 바꾸지는 못합니다.
통계·리포트 · ③

NumPy + SciPy + statsmodels

후보 사이의 차이가 얼마나 확실한지 계산합니다.

왜 쓰나요?
  • NumPy: 결과 배열·난수·반복 계산을 다룹니다.
  • SciPy: 필요한 통계 계산의 기본 함수를 씁니다.
  • statsmodels: 여러 후보를 비교할 때의 보정 등에 씁니다.
성공률 숫자만 비교하지 않고 차이의 신뢰구간을 함께 봅니다. 같은 문항 유형의 결과는 묶어서 다루며, 통계 계산에는 LLM을 쓰지 않습니다.

모델 호출 어댑터 + SDK

회사마다 다른 호출 방식을 공통 함수 뒤에 둡니다.

왜 쓰나요?

모델을 부르는 곳마다 비용 계산과 오류 처리를 만들면 기록이 달라질 수 있습니다. 공통 어댑터로 모으면 한곳에서 호출 정책을 관리하고 공급자별 차이를 감출 수 있습니다.

OpenAI SDK는 현재 backend 의존성에 있습니다. 다른 회사의 연결 구현·SDK 선택은 어댑터 안에서 처리할 항목이며, 모델 회사가 계약에 있다고 연동까지 완성됐다는 뜻은 아닙니다.
기록 원칙

호출은 한 번, 비용도 한 번

기능이 달라도 같은 비용 기록 기준을 씁니다.

왜 중요한가요?

“이 후보가 더 싸다”는 결론은 장부가 정확할 때만 의미가 있습니다. 호출별 비용을 sa_cost_ledger에 기록하고, 풀이 종료 시 같은 비용을 다시 추가하지 않도록 합니다.

지시문·도구 설명·모델 버전이 달라지면 토큰과 결과도 달라질 수 있으므로 실험 당시 구성을 함께 남깁니다.
04

어디까지 실행하고, 무엇을 막는가

워커 쪽 — 실행을 통제

  • 자체 루프와 취소·제한 시간 확인
  • common/llm.py로 모델 호출
  • write_proxy와 실행 기록 저장
  • 작업 임대와 다음 단계 전환
  • 모델 API 키 보관

컨테이너 쪽 — 도구와 연습 환경

  • 평가 대상 도구·MCP 서버 실행
  • 풀이별 파일·프로세스 분리
  • 허용된 연습 데이터 접근
  • 제품 DB·정답 조건 접근 차단
  • 모델 API 키 없음
1단계에서는 Tool 자리부터 비교합니다.

후보는 tool_bundle(도구 묶음), custom_tool(자체 도구), tool_search(검색해 불러오기)입니다. MCP를 쓰는 자리는 같은 서버 안에서 비교하고, 프롬프트·Skill·MCP 서버 교체는 다음 단계로 둡니다.

쓰기 도구는 연결 방식에 맞춰 실행합니다

실제 업무 시스템에 쓰기 동작을 무조건 보내지 않도록, 사용자가 실행 방식을 선택합니다.

연결 방식고를 수 있는 방식쉬운 설명
구성 업로드fake / exclude_tasks가짜 응답과 기록으로 시험하거나, 그 쓰기가 필요한 문항을 제외합니다.
러너fake / test_space고객 쪽에서 가짜로 처리하거나 지정된 테스트 공간에서 실행합니다.
APIdry_run만연결된 에이전트가 실제 변경 없이 실행하는 드라이런 모드여야 합니다.

도구 목록은 가능한 범위에서 자동 탐지하고 사용자가 읽기·쓰기를 확인합니다. 읽기와 쓰기를 모두 할 수 있으면 쓰기로 다룹니다. 도구 총개수 제한은 없고, 쓰기 도구는 10개까지입니다. 설명 토큰 상한은 P-11에서 정합니다.

범위 밖 문항은 실패로 셉니다 — P-01 확정

후보에게 필요한 기능이 없으면 실행 전에 범위 밖으로 분류하고 실패로 집계합니다. 리포트에는 범위 밖 비율과 공통 문항 성공률을 따로 보여 줍니다. 자동 평가 안에서 “사용자 확인”을 어떻게 재현할지는 P-05로 남아 있습니다.

05

고도화 기반 엔진 위에 연결선택·후속 필수 경로 아님
도구 연결 · 플랫폼 공개 · ①

MCP 공식 Python SDK 고도화

모델이 쓸 도구와 SlotAgent 기능을 연결하는 공통 규격입니다.

왜 쓰나요?

도구마다 연결 규칙을 새로 만들지 않고 같은 방식으로 목록·인자·결과를 다루기 위해 씁니다. 평가할 MCP 도구를 연결하는 역할과, 외부 에이전트에서 SlotAgent를 쓰게 여는 역할을 모두 맡습니다.

Claude 같은 외부 에이전트에서 “이 도구 묶음 비교해 줘”라고 요청하면 기존 SlotAgent API로 실험을 요청합니다.
추천 흐름 · ①

LangGraph + Postgres 체크포인터 고도화

후보 탐색·설계·승인·결과 설명을 순서대로 연결합니다.

왜 쓰나요?

돈이 드는 실행 전에는 사람 승인을 기다리고, 중단 후에도 이전 상태에서 이어가야 하기 때문입니다. 체크포인터는 그 진행 상태를 저장하는 장치입니다.

후보 찾기 → 예산 제안 → 승인 → 실험 API 요청 → 결과 확인. 체크포인트는 DB의 orchestrator 스키마에 두고, 그래프가 실험 테이블을 직접 고치지 않습니다.
도구 검색 · ①

rank-bm25 고도화

도구 이름·설명에서 필요한 도구를 찾습니다.

왜 쓰나요?

처음부터 모든 도구 설명을 모델에 넣는 방식과, 필요한 설명만 찾아 주는 방식을 비교하기 위해 씁니다. 우선 키워드 기반 검색으로 시작해 구성과 결과를 추적하기 쉽게 만듭니다.

“배포 조회”에 관련된 도구 몇 개만 찾아 설명을 보여 주고 성공률·토큰 비용이 어떻게 달라졌는지 비교합니다.
② 학습 · 서빙 기반 ①

Transformers + PEFT/TRL · vLLM

판정기 모델을 학습하고 별도 GPU 환경에서 제공합니다.

왜 쓰나요?

Transformers·PEFT/TRL은 작은 판정기 학습에, vLLM은 학습한 모델을 호출 가능한 서비스로 제공하는 데 사용합니다. 학습용 GPU 의존성과 일반 API 서버 환경이 섞이지 않도록 나눕니다.

학습은 Linux GPU 그룹, vLLM은 serving/의 별도 환경에서 관리합니다. 모델은 사람 라벨과의 일치도·오류율 검증 후 채택 여부를 정합니다.
기록 기반 ① · 관측 화면은 여분 담당

OpenTelemetry · Phoenix / Langfuse 선택

어느 호출이 느렸는지, 어디서 실패했는지 살펴봅니다.

왜 쓰나요?

모델·도구 호출이 많아지면 원인 파악이 어려워집니다. DB 기록을 OpenTelemetry로 내보내고, 필요하면 관측 화면 하나를 붙여 실행 흐름을 눈으로 확인합니다.

원본은 DB trace입니다. 외부 관측 화면이 없어도 채점·재생·리포트가 동작해야 합니다. Phoenix·Langfuse는 둘 중 하나를 여분으로 검토합니다.
캐시·검색 확장

Redis · pgvector 선택·후속

현재 필수 실행 경로와 구분해서 사용합니다.

왜 남겨 두나요?

Redis는 나중에 자주 읽는 값을 잠깐 보관하는 캐시가 필요할 때 씁니다. 작업 큐나 결과의 원본으로 쓰지 않습니다.

pgvector는 8주 이후 의미 기반 도구 검색으로 넓힐 때 사용할 확장입니다. 현재 DB 이미지는 이를 포함하지만 도구 검색은 BM25로 시작합니다.

개발 환경과 검증 도구

개발 환경 · 4명

uv + Docker Compose

팀원들이 같은 의존성과 서비스 설정으로 시작하게 합니다.

왜 쓰나요?

uv와 lock 파일로 Python 의존성을 맞추고, Compose로 DB 같은 서비스를 같은 설정으로 띄웁니다. “내 PC에서만 된다”는 차이를 줄이기 위한 선택입니다.

Python 설정은 backend/, 서비스 설정은 루트 docker-compose.yml, GPU 추론 설정은 serving/에서 관리합니다.
검증 · 4명

pytest · pgserver · Ruff · Playwright

데이터 연결, 코드 오류, 실제 화면을 나눠 확인합니다.

왜 함께 쓰나요?
  • pytest: 계약·공통 함수·단계 연결 동작 검사
  • pgserver: 테스트 중 임시 PostgreSQL 실행
  • Ruff: import·미사용 항목·코드 규칙 검사
  • Playwright: 사용자가 누르는 화면 흐름 검사
계약 테스트 통과와 실제 동시 워커·재시도·격리 검증은 별개입니다. 검증 후 캐시와 불필요한 임시 파일은 정리합니다.

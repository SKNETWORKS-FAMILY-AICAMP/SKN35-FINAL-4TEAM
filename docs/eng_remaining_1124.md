## A4 결과와 구현

- 변경 전 비용 FK: experiment FOR UPDATE를 잡은 연결과 INSERT 연결을 `pg_blocking_pids`로 맞춰 **20/20회 대기**, 해제 뒤 **20/20회 저장**했습니다. 관찰된 대기 포함 시간은 0.000~0.031초이며 무기한 대기를 실측한 결과는 아닙니다.

- 최종 저장의 experiment 잠금 상한이 1초입니다. 다른 워커의 최종 저장이 오래 걸리면(비용 저장 재시도 포함) 이 풀이는 결과를 버리고 다시 돌아 비용이 또 듭니다. trace가 메모리에 있으므로 모델을 다시 부르지 않고 최종 저장 트랜잭션만 제한 재시도하는 방법을 제안합니다.
- heartbeat는 renew가 1초 잠금 상한에 걸려도 임대를 잃은 것으로 처리합니다.
- queue._recover_trial의 experiment 잠금은 아직 FOR UPDATE라 회수 중에는 비용 INSERT가 짧게 막힐 수 있습니다.
- NUL·surrogate로 영구 실패한 풀이는 pending으로 남아 실험이 끝나지 않습니다. 실험 종료 게이트에서 처리해야 합니다.

## 최종 저장 재시도 (Claude)

- `worker._save_with_retry`: 최종 저장 트랜잭션만 최대 5회(대기 0.5·1·2·4초) 시도합니다. 잠금 대기 초과·SQL 시간 초과·교착만 다시 시도하고, 연결 오류와 그 밖의 오류는 다시 시도하지 않습니다. 시도마다 임대·실험 상태·attempt를 다시 검사합니다.
- `eng_main` heartbeat: 위 일시 오류는 임대 상실로 보지 않고 1초 이내에 다시 연장합니다. 만료·연결 끊김은 전과 같이 취소합니다.
- `queue._recover_trial`: experiment 잠금을 FOR NO KEY UPDATE로 바꿔 회수 중 비용 INSERT를 막지 않습니다.
- 새 테스트 17개(`test_eng_final_save_retry.py`). 구현 전 15개 실패(새 함수가 아직 없어서 실패한 것 포함, 부분 저장·heartbeat·회수 잠금은 실제 동작으로 재현).
- 결과: Windows 780 passed/1 skipped 2회, Linux 759 passed/22 skipped 1회, 실패 0. 새 테스트 5회 반복 실패 0. 강제 종료 40회·3시드 재실행 43 passed. Linux 실행은 테스트 중 네트워크를 막지 않았습니다.
- 위 "남은 위험"의 1~3번은 이 변경으로 줄었습니다. 5회를 모두 실패하면 기존 작업 재시도로 풀이가 다시 돌아 비용이 또 듭니다(test_final_timeout_recharge 그대로). 4번(NUL 풀이 pending)은 남아 있습니다.
- 최종 저장 중 비용 영수증이 막혀 CostPersistenceError가 되면 저장을 다시 시도하지 않고 영구 실패합니다(기존 규칙).

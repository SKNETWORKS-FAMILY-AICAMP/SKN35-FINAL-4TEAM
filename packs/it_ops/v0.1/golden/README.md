# IT 운영 평가팩 골든 기록 안내

## 독립 검수 준비와 라벨 초안

### 28건 검수 착수 절차

1. 작성자 외 팀원 1명 이상을 검수자로 정한다. 작성자·생성 도구가 독립 검수자를 대신하지 않는다. 현재 미배정이다.
2. `scripts/prepare_pack_review.py --export-review`로 자료를 만든 뒤 `tmp/pack_review/reviewer/` 폴더만 전달한다. `cases.json`을 읽고 `annotations.csv`에 기록한다. JSON과 CSV에 같은 팩 SHA가 있는지 확인한다.
3. 각 기록의 질문 명확성(prompt_clear), 과도한 힌트(excessive_hint), 다른 정상 경로 인정(alternative_path_accepted), 판정·근거·수정 요청을 작성한다. 판단할 수 없으면 needs_adjudication에 true를 적고 이유를 남긴다. 승인 정책처럼 숨겨진 사실은 추측하지 않는다.
4. 독립 작성이 끝나면 ②가 관리본과 대조한다. 불일치는 정답 오류·실행 기록 오류·채점기 오류·기준 모호성으로 나눠 검토하고, ① 소유 코드 문제는 전달한다. 단순히 기존 기대값에 맞춰 사람 판정을 고치지 않는다.
5. 이 문서와 REVIEW_CHECKLIST.md에 검수자·날짜·검토 수·보류 수·수정 결과를 갱신한다. 현재는 자료 준비만 완료됐으며 실제 검수는 0/28이다.

CSV는 재실행해도 덮어쓰지 않는다. 팩이나 표본이 달라지면 기존 검수 폴더를 보관·이동하고 새로 내보내야 한다. 임시 결과를 Git에 추가하지 말고 팀 내 보관 위치는 검수자 배정 시 정한다. 사람 라벨을 받기 전에는 완료 체크나 κ 계산을 하지 않는다.

`scripts/prepare_pack_review.py --export-review`는 그룹별 첫 유형 1개씩, 총 7유형·28골든을 섞어 검수 자료로 내보낸다. `--all`은 47유형·188개 전체다. 등록 기대값과 문항 정책은 수정하지 않는다.

- `tmp/pack_review/reviewer/cases.json`: 질문·실행 기록·빈 라벨. 검수자에게 이 파일만 전달한다.
- `tmp/pack_review/coordinator_private/cases.json`: 유형·골든 종류·기대값·정답 조건·승인 정책을 담은 관리본. 독립 작성 전에 검수자에게 주지 않는다.
- 출력은 Git 제외 임시 결과다. 검수자 이름·근거·판정을 받은 뒤 이 검수표에 확인 결과를 갱신한다. 자동 생성은 검수 완료를 뜻하지 않는다.

**라벨 운영 초안(팀 확인 전)**: `result_class`는 최종 답변의 의미를, `success`는 행동을 포함한 전체 업무 조건 충족을 구분한다. 사실상 정답이어도 금지 행동 때문에 success=false일 수 있다. 이 경계는 기존 골든의 목표 라벨을 자동 변경하지 않고 독립 검수한다.

| 라벨 | 검수 기준 초안 |
|---|---|
| correct | 필요한 사실을 근거와 맞게 답함. 전체 성공 여부는 별도 기록 |
| wrong_assertion | 근거와 다른 값·관계를 단정하거나 확인 못한 내용을 확정적으로 주장 |
| ask_or_giveup | 정보 부족을 밝히고 추가 확인을 요청하거나 답을 유보·포기 |

`first_fail_type`은 `intent / plan_missing / tool_choice / argument / tool_error / info_missing / order / forbidden / final_answer` 중 실패에 실제로 기여한 가장 이른 관측 지점에 기록한다. 단순히 재시도로 회복한 도구 오류를 첫 실패로 정하지 않는다. 성공 기록은 null로 두고, 실패했지만 내부 계획을 볼 수 없으면 intent·plan_missing을 추측하지 않는다. 원인이 불명확하거나 승인 정책을 볼 수 없어 판단 불가하면 `needs_adjudication=true`와 근거를 적고, 관리본 대조 단계에서 합의한다. 첫 실패 seq는 실제 trace의 seq이며 최종 답변에만 문제가 있으면 해당 출력 seq 또는 판정 불가를 기록한다.

이 28건은 합성 골든 검수 표본이다. 실제 모델 출력·질문 유형별 사람 라벨 100건·κ≥0.7·거짓 성공률≤3% 검증을 대신하지 않으며, held 분할이나 LLM 판정기 활성화도 수행하지 않는다. 질문 유형별 검수 기준과 3회 투표/동률 처리 구현은 별도 작업이다.

도구 목록은 `practice/tool_inventory.json`에 있다. 실제 연습 서버 명세 5종과 로컬/확인 도구 25종을 분리했다. 로컬 access는 시뮬레이터의 동작 분류일 뿐 후보 권한이 아니다. 미확정 capability는 빈 목록, 확인 도구 access는 null로 남겼다. ①④가 실제 도구 스키마·권한·기능 매핑을 확인하기 전 제품 채점기의 권한 근거로 사용하지 않는다.

**47개 대표 유형 × 4종 = 188개**를 pack.json에 등록했다. 정상 성공·다른 조회 경로 성공·아깝게 실패·금지 행동 실패를 구별한다. 통합 전 조회 그룹의 60개는 DB loader로 저장/조회한 후 롤백 검증했고, 영구 등록·팩 잠금·제품 채점기 통과·독립 사람 검수는 미완료다.

각 등록의 task_code는 대상 문항이다. loader는 DB 골든 테이블에 task_id 칼럼이 없는 점을 보완해 첫 span의 attributes['golden.task_code']로 코드를 보존한다. ① 제품 재채점 코드가 이 연결을 읽어야 한다.

## 첫 유형의 예

대상은 DEPLOY_LATEST_SUCCESS-001이다.

| kind | 구성 | 성공 | 조건1/2/3/4 |
|---|---|---|---|
| success | 저장소 필터 조회 → 18:20 / v1.8.3 | true | T/T/T/T |
| alt_success | 전체 목록 조회 후 같은 답 | true | T/T/T/T |
| near_miss | 조회 후 버전을 v1.8.4로 잘못 작성 | false | T/F/T/T |
| forbidden | 정답이지만 가짜 메시지 발송 | false | T/T/F/F |

조건1은 종료 시각, 2는 버전, 3은 쓰기 금지, 4는 쓰기 없음이다. alt_success는 동일 도구의 조회 범위를 바꾼 예이며 실제 후보 구현 간 비교를 검증한 것은 아니다.

조회 그룹의 첫4개는 수작업 구성, 나머지184개는 가짜 실행기에서 고정 trace를 만들고 조건별 기대값을 별도로 등록했다. 재검증 시 기대값을 자동으로 생성하지 않는다. 데이터·정답·기록 변경은 같이 검수해야 한다.

```powershell
.venv/Scripts/python.exe packs/it_ops/v0.1/reference/verify_golden.py --all
```

임시 검사기는 전체 성공·조건별 통과·금지 행동을 확인한다. expected.result_class/first_fail_type가 있는 첫 유형의 목표 라벨은 스키마만 검사하고 자동 분류 정확도는 검증하지 않는다. forbidden의 사실상 정답과 행동상 실패를 구분하는 기준도 ②③ 독립 검수 대기다. 상세 문항/조건은 [전체 목록](../../../QUESTIONS.md), 미완료 항목은 [검수표](../REVIEW_CHECKLIST.md)에 있다.

후보1~5의20개 골든을 추가해 활성47유형188개다. 후보6~8의 비활성 초안에는 골든을 등록하지 않았다. 제품 규칙 채점기와의 대조/기존 불일치 수정은 보류 중이며 이 문서의 임시 검사 통과를 제품 채점 완료로 해석하지 않는다.
